### What happened?
When the node that runs the **single `barman-cloud` plugin pod** fails along with the primary, the operator **does not fail over** until Kubernetes evicts the plugin pod (default 300 s `tolerationSeconds`) and reschedules it. During that time the Cluster phase is:

```
Cluster cannot proceed to reconciliation due to an error while interacting with plugins
```

and the `-rw` service has no endpoints. So a backup plugin becomes a single point of failure for HA.

**Reproduction**
1. `cluster-example` (3 instances) with `.spec.plugins: [{name: barman-cloud.cloudnative-pg.io, isWALArchiver: true, parameters: {barmanObjectName: ...}}]`.
2. Primary and `barman-cloud` plugin pod on the same worker; operator on another worker.
3. Hard power-off that worker (`echo o > /proc/sysrq-trigger`), or fully network-partition it.

**Measured write outage on `cluster-example-rw`** (new connection + INSERT every ~200 ms):
- plugin on the failed node: **401 s** (failover happened right after the plugin pod was rescheduled, at ~400 s)
- 240 s full partition with the plugin on the isolated node: **no failover at all** during the partition (~244 s outage)
- same failure with the plugin on another node: **74 s** (node crash) / **97 s** (partition), consistent with the documented 40–55 s detection

**Expected:** the failover of a primary that is unreachable should not depend on a backup/WAL-archiver plugin being reachable, or this dependency should be clearly documented, with guidance to run the plugin with 2+ replicas and anti-affinity. Possibly related: #9770.
