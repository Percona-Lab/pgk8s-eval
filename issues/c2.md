### What happened?
When the **node running the primary loses its connection to the API server** but the pod network stays up (in our test the kubelet's connection to the API server was cut; pods on that node could still reach the API server and their peers through the overlay), the node goes `NotReady`. Kubernetes then marks the primary pod not ready, and it is removed from `cluster-example-rw`. The primary itself stays healthy and keeps accepting local writes, and the operator does not fail over (phase stays `Cluster in healthy state`), because the instance manager is still reachable.

Result: **136 s of write outage** through `-rw` with a healthy primary and no failover, until the node became Ready again.

For comparison, a Patroni-based operator on the same nodes (Percona Operator for PostgreSQL 3.1.0, whose primary Service endpoints are written by Patroni rather than selected by readiness) had no write interruption in the same test.

**Reproduction:** on the primary's worker, drop host traffic to the API server's IP (`iptables -I OUTPUT -d <apiserver-ip> -j DROP`, plus INPUT) for ~3 minutes, while flannel's VXLAN keeps using another interface or IP. Run a write probe against `cluster-example-rw`.

**Expected:** either fail over (the primary is effectively unreachable to clients), or keep the `-rw` endpoint while the instance manager reports a healthy primary, or at least document this failure mode in failure_modes/failover.
