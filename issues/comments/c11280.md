Independent reproduction on **1.30.1** (the release that carries #11518, #11347 and #11356), following the method from the Coroot post.

**Setup:** k3s v1.35.9, 1 tainted control-plane node + 3 workers (2 vCPU / 4 GB), local-path storage. `cluster-example` (3 instances, PG 18.6), async replication, defaults: `smartShutdownTimeout: 180`, `failoverDelay: 0`, isolation check enabled. Three writers on the control-plane node hold persistent connections through `-rw` and insert a row every ~100 ms, logging each acknowledged id and commit timestamp.

**Fault:** iptables rules inside the primary pod's network namespace drop everything except the client pods' subnet and the node's own pod CIDR, which keeps the kubelet's probes working. That cuts the pod off from the replicas, the operator, the barman-cloud plugin and the API server (10.43.0.0/16). The partition lasted 300 s.

**Result with defaults (1.30.1):**
| Event | Time after partition |
|---|---|
| New primary ready (`database system is ready to accept connections`) | +77.4 s |
| Old primary's last acknowledged write | +206.7 s |
| **Dual-primary window** | **129.3 s**, with 3,680 writes acknowledged by the old primary during it |
| Writes acknowledged by the isolated old primary after the partition | 5,905, **all absent from the final table** after rejoin |

So the window described here is still present in 1.30.1.

**Same fault with the mitigations** (one run each):
| Configuration | Old primary's last ack | New primary ready | Overlap | Acked writes lost |
|---|---|---|---|---|
| `smartShutdownTimeout: 0` | +23.3 s | +73.8 s | none | 660 (async lag before fencing) |
| `smartShutdownTimeout: 0`, `failoverDelay: 30` | +25.7 s | +107.6 s | none | 740 |
| `synchronous: {method: any, number: 1, dataDurability: required, failoverQuorum: true}` | no acks after partition | +76.4 s | none | **0** |

With quorum sync, the writers' sessions stayed blocked on the old primary until the smart shutdown expired (+207 s), so they could not reach the new primary for about 130 s after it was ready.

**Two related observations on 1.30.1:**
- **API server and replication cut, operator port 8000 open:** we blocked the primary's node from the API server, and blocked the primary pod from the API server and from 5432 to and from the replicas. No failover happened in 300 s, and existing sessions kept writing safely with no loss. New connections through `-rw` failed for 264 s, because the node went NotReady (see also #11656).
- **120 s cgroup freeze of the primary pod plus SIGSTOP of the k3s agent (approximating a VM pause):** the replica was promoted at +67.3 s. After the thaw, the old primary committed 409 writes from already-open sessions in about 1 s before it was shut down (#11347 appears to bound this). All 409 were lost. A 30 s freeze caused no failover and no loss.
