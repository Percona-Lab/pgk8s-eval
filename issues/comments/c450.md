Additional measurements for the proposed failure-scenarios page, from operator 3.1.0 with default settings on the same lab. Three writers hold persistent connections and log every acknowledged commit.

| Scenario | Old primary stops acknowledging writes | New leader promoted | Dual-primary overlap | Acknowledged writes lost (async) |
|---|---|---|---|---|
| Primary pod network-partitioned from replicas, operator and API server, with clients still connected (direct to `cluster1-primary`) | +13.6 s (Patroni: "demoting self because DCS is not accessible") | +26.9 s | none | 391 |
| Same, clients through pgBouncer | +19.2 s | +32.5 s | none | 368 |
| Node loses the API server, primary pod loses the API server and 5432 to the replicas | +10.5 s | +21.8 s | none | 305 |
| 120 s freeze of the primary pod plus kubelet (VM-pause approximation) | 0.3 s after thaw (`Demoting self (immediate-nolock)`) | +26.9 s | ~0.3 s after thaw | 53 |

**Worth documenting:**
1. **Split-brain safety comes from the DCS TTL.** Patroni demotes an isolated primary once it cannot renew the leader key in the Kubernetes API, before a replica can take the lock. The same partition on CloudNativePG 1.30.1 gave a 129 s dual-primary window with defaults (cloudnative-pg/cloudnative-pg#11280).
2. **Writes acknowledged before demotion are lost with async replication.** That was 10–19 s of writes in these runs. The page should say so and point to synchronous replication via `patroni.dynamicConfiguration` for zero-loss requirements.
3. **A long pause (VM migration, freeze) can let a stale primary commit briefly after it resumes.** Patroni demoted within 0.3 s, but sessions that were already open still got about 50 commits acknowledged.
