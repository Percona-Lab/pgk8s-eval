Page: `migrate-from-crunchy-backup-restore.md`

The guide assumes the Crunchy cluster's S3 repository is `repo1` and asks the reader to reconfigure the Crunchy cluster. But in Crunchy's own examples `repo1` is a **PVC** repo, so in existing Crunchy deployments the object-store repo is often `repo2` (or later).

Please document:
1. **Repo index mapping.** `dataSource.pgbackrest.repo.name` must be `repo1` and the Secret must use `repo1-*` keys, even when the source repo is `repo2`. Point `repo1-path` at the source's `repo2-path`. We restored this way from Crunchy v6.0.3 `repo2` (ready in 50 s, data complete). Related: #451.
2. **PVC-only Crunchy repos.** The current page has no path for clusters with only `repo1` on a volume.
3. **PITR at cutover.** `--type=time` in `dataSource.pgbackrest.options`, or a final `pg_switch_wal()` plus backup, so the restore reaches the last write.
4. Link the "what is not migrated" section (passwords, extensions, pg_cron, schema default). In our run, the documented defaults dropped `pg_stat_statements` and `set_user`, and left pg_cron jobs dormant.

Evidence (scripts, logs): https://github.com/Percona-Lab/pgk8s-eval (`crunchy/`, `results/mig*`, `FINDINGS.md`). Tested with Percona Operator 3.1.0 and Crunchy PGO v6.0.3 on k3s.
