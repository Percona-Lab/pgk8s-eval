Page: `migrate-from-crunchy-data-volumes.md`

1. **The PVC `selector` can deadlock on `WaitForFirstConsumer` storage.** We followed the page with local-path storage. The scheduler placed the new instance on a node other than the retained PV's node, and the provisioner then failed with `claim.Spec.Selector is not supported`. The pod stayed `Pending` for 10 minutes. Pinning the instance to the PV's node (`instances[].affinity.nodeAffinity` with `kubernetes.io/hostname`, or the zone for zonal cloud disks) fixed it: writable in 26 s. Please add this step, and a troubleshooting entry with the exact error. Product request filed in percona-postgresql-operator.
2. **No clean shutdown.** The page removes finalizers and deletes the running `PostgresCluster`. Recommend `spec.shutdown: true` first, waiting for the pods to stop, so PGDATA is cleanly shut down before reuse.
3. **WAL and tablespace volumes.** Clusters with `walVolumeClaimSpec` or tablespaces need those PVs retained and bound too. The page only covers `pgdata`.
4. **Measured downtime (Crunchy v6.0.3, 332 MB) once pinned:** about 45 s from the last write to the Percona primary being writable.

Evidence (scripts, logs): https://github.com/Percona-Lab/pgk8s-eval (`crunchy/`, `results/mig*`, `FINDINGS.md`). Tested with Percona Operator 3.1.0 and Crunchy PGO v6.0.3 on k3s.
