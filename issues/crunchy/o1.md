**Environment:** Percona Operator 3.1.0 (images 18.6.1-3, pgBouncer 1.25.2-8, pgBackRest 2.59.1-2), source Crunchy PGO v6.0.3 (PG 18.6), k3s 1.35.9, 3 workers, local-path storage, S3-compatible object store.

## Summary
When a built-in extension is not enabled in `spec.extensions` (the default for `pg_stat_statements`, `set_user`, `pg_repack`, `pg_cron`, `pgvector`), the operator runs `DROP EXTENSION IF EXISTS ...` in **every database** (`internal/pgstatstatements`, `internal/setuser`, `internal/pgrepack`, `internal/pgvector`; `pg_cron` only in `postgres`). Any cluster that already contains these extensions loses them silently. That includes clusters migrated from Crunchy PGO, restored from older backups, or ones where users ran `CREATE EXTENSION` themselves.

## Reproduction (Crunchy → Percona, documented backup/restore method)
1. Source Crunchy cluster, database `hippo`: `pg_cron`, `pg_partman`, `pg_stat_statements`, `set_user`, `plpython3u`, `pgaudit`.
2. Create a PerconaPGCluster with `dataSource.pgbackrest` pointing to the Crunchy S3 repo, using `deploy/cr.yaml` defaults (no `extensions` block).
3. After the cluster is `ready`, `hippo` contains: `pg_cron, pg_partman, pgaudit, plpgsql, plpython3u`. **`pg_stat_statements` and `set_user` are gone.**

Nothing is reported in status or events. Objects that depend on the extensions (for example views on `pg_stat_statements`, and set_user's privilege setup) break or vanish.

## Expected
The operator should not drop extensions it did not create. Suggested fix:
- Make each built-in tri-state: `enabled` (create), `disabled` (drop, explicit opt-in), and unset or unmanaged (leave alone, the new default).
- At minimum, never drop on clusters bootstrapped from `dataSource` or `standby`, and emit an Event before dropping.

Evidence (scripts, logs, manifests): https://github.com/Percona-Lab/pgk8s-eval (see `crunchy/`, `results/mig*`, `FINDINGS.md`).
