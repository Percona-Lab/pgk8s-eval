**Environment:** Percona Operator 3.1.0 (images 18.6.1-3, pgBouncer 1.25.2-8, pgBackRest 2.59.1-2), source Crunchy PGO v6.0.3 (PG 18.6), k3s 1.35.9, 3 workers, local-path storage, S3-compatible object store.

## Summary
When `extensions.pg_cron.enabled: true`, the operator adds a **mandatory** `cron.database_name = postgres` (`internal/pgcron/postgres.go`, `PostgreSQLParameters`) and creates the extension only in `postgres`. Clusters where pg_cron lives in an application database (common on Crunchy PGO, where users set `cron.database_name` themselves) keep their `cron.job` rows, but the jobs **never run again**.

## Reproduction
1. Crunchy source: `cron.database_name=hippo`, with two jobs in `hippo` (`partman.run_maintenance_proc()` every 5 min and a heartbeat insert every minute).
2. Migrate to Percona (backup/restore), then enable `extensions.pg_cron`.
3. `SHOW cron.database_name` returns `postgres`. `cron.job` in `hippo` still lists both jobs, but there are no new `cron.job_run_details` rows and no heartbeat rows after migration. The last heartbeat was written on the Crunchy source.

## Expected
Honour a user-supplied `cron.database_name` (from `spec.patroni.dynamicConfiguration` / `config.parameters`), and create or alter the extension in that database. Default to `postgres` only when nothing is set. At minimum, document the behaviour and how to move jobs (`cron.schedule_in_database`).

Silently stopped jobs are especially harmful with pg_partman: the tables eventually run out of future partitions.

Evidence (scripts, logs, manifests): https://github.com/Percona-Lab/pgk8s-eval (see `crunchy/`, `results/mig*`, `FINDINGS.md`).
