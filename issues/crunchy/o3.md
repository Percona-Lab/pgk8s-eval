**Environment:** Percona Operator 3.1.0 (images 18.6.1-3, pgBouncer 1.25.2-8, pgBackRest 2.59.1-2), source Crunchy PGO v6.0.3 (PG 18.6), k3s 1.35.9, 3 workers, local-path storage, S3-compatible object store.

## Summary
The volume-reuse migration path (docs: *Migrate reusing data volumes*) binds the retained PV through `dataVolumeClaimSpec.selector`. With a **`WaitForFirstConsumer`** StorageClass (local-path here, and many CSI drivers), the scheduler picks a node before binding. If that node can't reach the PV (local disk on another node, or a zonal disk in another zone), the PVC falls back to dynamic provisioning. The provisioner then rejects the selector and the instance pod stays `Pending` forever:

```
Warning ProvisioningFailed ... failed to provision volume with StorageClass "local-path": claim.Spec.Selector is not supported
PodScheduled=False SchedulerError: running PreBind plugin "VolumeBinding": binding volumes: context deadline exceeded
```
In the lab the PVC got `volume.kubernetes.io/selected-node=pk-w3`, while the PV's node affinity was `pk-w2`. The migration hung for 10 minutes, mid-cutover, until the instance was pinned with `affinity.nodeAffinity`. After that the primary was writable in 26 s.

## Suggestions
- Support static binding in `dataVolumeClaimSpec` (`volumeName` and/or `storageClassName: ""`), or derive node or zone affinity from a referenced PV automatically.
- Accept WAL and tablespace PVs in the same flow (`dataSource.volumes` already has `pgWALVolume`).
- Surface the stuck state in `PerconaPGCluster` status. Today it only shows `initializing`.

Evidence (scripts, logs, manifests): https://github.com/Percona-Lab/pgk8s-eval (see `crunchy/`, `results/mig*`, `FINDINGS.md`).
