**Environment:** Percona Operator 3.1.0 (images 18.6.1-3, pgBouncer 1.25.2-8, pgBackRest 2.59.1-2), source Crunchy PGO v6.0.3 (PG 18.6), k3s 1.35.9, 3 workers, local-path storage, S3-compatible object store.

## Summary
In the documented Crunchy → Percona standby migration, the Percona cluster is configured with the **same pgBackRest repo path** as the Crunchy source, and keeps archiving there after promotion. Nothing prevents a second primary that uses the same repo from archiving into it too.

## What we observed
After cutover (Crunchy put into standby and shut down, Percona promoted on timeline 6), we started Crunchy again **without** first putting the Percona cluster back into standby. That is step 2 of the documented rollback, and we skipped it. Crunchy replayed Percona's post-cutover WAL from the shared repo, promoted to timeline 7, and both primaries then archived into the same stanza without any error:

```
crunchy: timeline 7, last_archived_wal 000000070000000000000036, failed_count 0
percona: timeline 6, last_archived_wal 000000060000000000000037, failed_count 0
pgbackrest info: wal archive min/max (18): 000000010000000000000001/000000070000000000000036
```
A later PITR or replica creation from this repo can pick the other cluster's history.

## Suggestions
- While in standby, read from the source repo. After promotion, write to a **new** repo path (or require one in the CR for standby migrations).
- Refuse, or raise a condition and Event, when the cluster's timeline is behind the repo's latest timeline for the same system ID, which indicates another writer.
- Related docs issue: rollback guidance in the standby migration guide (filed separately in k8spg-docs).

Evidence (scripts, logs, manifests): https://github.com/Percona-Lab/pgk8s-eval (see `crunchy/`, `results/mig*`, `FINDINGS.md`).
