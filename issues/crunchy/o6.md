## Feature request: adopt a running Crunchy PGO cluster in place

Percona Operator is a fork of Crunchy PGO v5, and in our lab with Crunchy **v6.0.3** the in-cluster formats already matched:
- Service names (`-primary`, `-ha`, `-replicas`, `-pgbouncer`)
- Secret names and keys
- Patroni scope and DCS (Kubernetes endpoints)
- pgBackRest stanza `db` and repo layout
- PGDATA layout
- the generated PostgreSQL and pgBouncer configuration
- the internal roles (`_crunchyrepl`, `_crunchypgbouncer`)

Since 3.0 (the `upstream.pgv2.percona.com` rename), both operators also coexisted in one cluster without interference.

That makes an **adoption** mode possible, which no other operator can offer Crunchy users:
1. The user scales the Crunchy operator to 0.
2. Percona creates a `PerconaPGCluster` that references the existing `PostgresCluster` objects (StatefulSets, PVCs, Services, Secrets) and takes ownership without deleting them.
3. Percona swaps images instance by instance (replicas first, then a switchover). The images must be compatible: same PG major, and extensions present (see the parity issue).

The result is migration as a rolling restart: no data copy, no new endpoints, no password change, and no application change. All three current methods require at least one of those.

Evidence (scripts, logs, manifests): https://github.com/Percona-Lab/pgk8s-eval (see `crunchy/`, `results/mig*`, `FINDINGS.md`).
