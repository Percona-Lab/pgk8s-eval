Docs version: 3.1.0 (https://docs.percona.com/percona-operator-for-postgresql/latest/), checked 2026-10-13 alongside hands-on tests with operator 3.1.0.

## 1. Patroni timing options are described incorrectly
`operator.md#patronileaderleasedurationseconds` describes `patroni.leaderLeaseDurationSeconds` as the "initial delay for liveness/readiness probes". It is the Patroni leader **TTL** (default 30 s), and `syncPeriodSeconds` is Patroni `loop_wait` (10 s). These two values decide how fast a failover happens. In our tests a node power-off gave a ~27–31 s write outage, which matches the TTL. Please describe the mapping to Patroni `ttl`/`loop_wait` and mention that Patroni uses the Kubernetes API as its DCS.

## 2. No page on failure behaviour
There is no page explaining what happens, and how long it takes, when the primary pod is deleted, postgres crashes, the primary's node is lost or partitioned, or the operator is down. Measured on 3.1.0 with default settings (write outage, direct to `cluster1-primary`):
- primary pod deleted 2.4 s
- postmaster kill -9 (restarted in place) 10.8 s
- planned switchover 2.4 s
- primary deleted with operator scaled to 0: 3.4 s, so Patroni fails over without the operator, a strong point worth documenting
- node power-off 27 s
- full network partition 31 s; the isolated old primary refused writes after ~15 s, so no split-brain
- if the pgBackRest repo-host is on the lost node, promotion stalls (separate issue)

Also missing: a runbook for **permanent node loss with local storage**. What worked was force-deleting the stuck pod and deleting its PVC, for the instance and for the repo-host; the operator then rebuilt both.

## 3. Errors on the live site
- `debug-shell`: example `hostname` output is `cluster1-pxc-0` (copied from the PXC docs) and the log path is `/pgdata/pg16/log` although the default is PG 18.
- `troubleshoot-operator`: "The cluster should typically be in the `Running` state"; the PerconaPGCluster status is `ready`.
- `backups-pitr-inplace`: the time format is given as `<YYYY-MM-DD HH:MM:DD>`; it should be `HH:MM:SS`.
- `compare.md`: lists PostgreSQL "13 - 18", but PG 13 was removed in 2.9.0.

## 4. Default backup duration
The first on-demand full backup with default options took ~5 min for a 337 MB database, because pgBackRest waits for a spread checkpoint (`start-fast=n`). With `--start-fast` it took 43 s end to end. A note in the backup docs (or `--start-fast` in the example `backup.yaml`) would avoid "backups are slow" reports.
