**Environment:** Percona Operator 3.1.0 (namespace-scoped installs in `pct-a` and `pct-b`), PG 18.6 (18.6.1-3), pgBackRest 2.59.1, k3s 1.35.9, S3-compatible object store. One instance per cluster; the two namespaces simulate two sites.

## Summary
After a `PerconaPGCluster` is deleted and recreated with the **same name**, the new cluster never takes its initial backup. It still reports `status.pgbackrest.repos[0].replicaCreateBackupComplete: true` and `ReadyForBackup` is satisfied. The cause appears to be a `PerconaPGBackup` left over from the deleted cluster: it has **no ownerReference**, survives the deletion, and the new cluster treats it as its initial backup.

## Reproduction
1. Create `dra` with an S3 repo at `/pgbackrest/dr/repo1`. The initial backup `dra-backup-qhss-*` succeeds.
2. `kubectl delete pg dra` and delete its PVCs.
3. Recreate `dra` with a **new** repo path (`/pgbackrest/dr2/repo1`).
4. `kubectl get perconapgbackup` still shows the old `dra-backup-qhss-vgr89  Succeeded  2026-10-14T13:05:38Z` with `OWNER <none>`.
5. The new cluster reports `replicaCreateBackupComplete: true`, but `pgbackrest info` shows `status: error (no valid backups)`.
6. A standby cluster bootstrapping from that repo then crash-loops:
```
WARN: repo1: [BackupSetInvalidError] no backup sets to restore
ERROR: [075]: no backup set found to restore
patroni.exceptions.PatroniFatalException: Failed to bootstrap cluster
```
A manual `PerconaPGBackup` (`--type=full`) fixed it.

## Expected
- `PerconaPGBackup` objects should be owned by, or reliably cleaned up with, their cluster. Alternatively, the initial-backup check should match on cluster UID and repo, not on name.
- `replicaCreateBackupComplete` should never be true while the configured repo has no valid backup.

Besides breaking standbys, this leaves a new cluster without any backup while its status says it has one.

Evidence (scripts, logs, manifests): https://github.com/Percona-Lab/pgk8s-eval (see `dr/`, `results/dr_*`, `FINDINGS.md` → "Cross-site DR switchover").
