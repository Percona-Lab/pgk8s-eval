## Feature request: safe planned switchover between a primary cluster and a standby cluster

**Environment:** Percona Operator 3.1.0 (namespace-scoped installs in `pct-a` and `pct-b`), PG 18.6 (18.6.1-3), pgBackRest 2.59.1, k3s 1.35.9, S3-compatible object store. One instance per cluster; the two namespaces simulate two sites.

Percona standby clusters cover cross-site DR. A **planned** role swap, e.g. a site move, a DC test or "return home" after DR, has no operator support and no documented procedure. The obvious sequence (set `standby.enabled: true` on the primary, wait, set `standby.enabled: false` on the standby) behaves very differently depending on the standby type.

## Measured (single runs, 3 writers logging every acknowledged commit)
| Standby type | Procedure | Write downtime | Acked writes lost | Old primary |
|---|---|---|---|---|
| Repo-only (S3) | demote A → wait until B's replay LSN is stable for 15 s → promote B | 24.7 s | 0 of 819 | **Diverged and stuck.** A ended at `0/70000A0` (shutdown checkpoint in an unarchived segment); B only got `0/7000000`. A logs `new timeline 2 forked off current database system timeline 1 before current recovery point 0/70000A0` and never follows B |
| Streaming + repo | same | 24.2 s | 0 of 853 | Streams from B at once, no rebuild |
| Streaming + repo | demote + promote with no wait | 1.9 s | 0 of 946 | Diverged slightly; **Patroni ran pg_rewind automatically**, then streamed |

For comparison, CloudNativePG 1.30's distributed topology runs the same switch archive-only. It archives the demoted primary's final WAL as `.partial`, publishes a `demotionToken` with the shutdown checkpoint LSN, and promotes the replica only after it reaches that LSN. Result: 8.5 s, 0 of 808 lost, and the old primary rejoined without a rebuild.

## Proposal
1. On `standby.enabled: false → true` for a primary, archive the final (partial) WAL segment to the repo and record the demotion LSN, timeline and system identifier in `status.standby`.
2. Add an optional `standby.promoteAfterLSN` (or a `PerconaPGSwitchover`-style resource) that promotes only after the standby has replayed to that LSN.
3. Surface progress in status: target LSN, replayed LSN, timeline.
4. Document the procedure (filed separately in k8spg-docs).

This is the main gap against CloudNativePG for DR deployments where the sites share object storage but have no network path.

Evidence (scripts, logs, manifests): https://github.com/Percona-Lab/pgk8s-eval (see `dr/`, `results/dr_*`, `FINDINGS.md` → "Cross-site DR switchover").
