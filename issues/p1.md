**Operator version:** 3.1.0 (deploy/bundle.yaml + deploy/cr.yaml, images as pinned in cr.yaml, PG 18.6)
**Environment:** k3s v1.35.9+k3s1, 1 control-plane + 3 workers (Linode 2 vCPU / 4 GB, Ubuntu 24.04), local-path storage, S3-compatible object store with TLS.

## Summary
When the node running the **primary** also runs the **pgBackRest repo-host** and that node is lost, Patroni acquires the leader lock on a replica within ~30 s, but PostgreSQL on the new leader stays read-only for minutes. Promotion is blocked by `restore_command` (`pgbackrest archive-get`) timing out 60 s per call against the unreachable repo-host (repo1).

## Steps to reproduce
1. Default cr.yaml (3 instances, repo1 = PVC on repo-host), plus repo2 = S3.
2. Arrange (or wait) for the primary and `cluster1-repo-host-0` to be on the same node.
3. Hard power-off that node (`echo o > /proc/sysrq-trigger`), or fully network-partition it.
4. Run a write probe against `cluster1-primary`.

## Observed
- Patroni on the new leader: `promoted self to leader by acquiring session lock` at T+27 s.
- Clients keep getting `ERROR: cannot execute INSERT in a read-only transaction` from the new leader.
- PostgreSQL log on the new leader:
```
21:34:20.042 LOG:  received promote request
21:35:20.343 P00   WARN: repo1: [HostConnectError] timeout connecting to 'cluster1-repo-host-0.cluster1-pods...:8432'
21:36:20.655 P00  ERROR: [082]: unable to get WAL file '000000060000000000000036' from the archive asynchronously after 60 second(s)
21:36:20.779 P00   WARN: repo1: [HostConnectError] timeout connecting to ...
21:37:21.069 P00   WARN: repo1: [HostConnectError] timeout connecting to ...
21:37:21.096 LOG:  selected new timeline ID: 7
21:37:58.969 LOG:  restored log file "00000006.history" from archive
21:37:58.995 LOG:  database system is ready to accept connections
```
- **Write outage: 271 s** (node power-off for 10 min) and ~243 s (partition test), against **27–31 s** for the same node failure when the repo-host is on a different node.
- `kubectl get pg` showed `ready` / `initializing` the whole time, and the new leader already carried `role=primary`, so nothing pointed at the cause.

## Expected
Promotion should not depend on the availability of a single backup pod. Possible fixes:
- shorter archive-get timeouts during promotion, or prefer object-store repos for history lookups;
- default anti-affinity between the repo-host and the instances, or at least a documented recommendation;
- a status condition when promotion is waiting on restore_command.
