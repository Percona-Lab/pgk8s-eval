**Operator version:** 3.1.0, pgBackRest 2.59.0, repo1 = PVC on repo-host + repo2 = S3
**Environment:** k3s v1.35.9+k3s1, 1 control-plane + 3 workers (Linode 2 vCPU / 4 GB, Ubuntu 24.04), local-path storage, S3-compatible object store with TLS.

## Summary
If one configured repo is unreachable (here the repo-host's node was lost), **every WAL archive-push fails**, although repo2 (S3) is healthy. pgBackRest pushes to all repos, so WAL piles up in `pg_wal` on the primary until the repo-host is back or is rebuilt manually.

## Observed (new primary after node loss)
```
21:47:24 P00  ERROR: [082]: unable to push WAL file '00000009.history' to the archive asynchronously after 1m second(s)
21:48:25 P00  ERROR: [082]: unable to push WAL file '00000009000000000000003A' to the archive asynchronously after 1m second(s)
21:49:25 ... 3B ... 21:50:26 ... 3C ... 21:51:26 ... 3D
```
`kubectl get pg` still reported `ready`.

## Expected
- Archiving to the healthy repo should continue (pgBackRest `archive-mode-check` / `archive-push-queue-max`, or per-repo handling), or
- the operator should surface a clear condition/event that archiving is failing, with the risk of filling pg_wal.

With local-storage repo-host PVCs, losing one node permanently means manually force-deleting the repo-host pod and its PVC (this worked: the operator recreated the stanza). That procedure is not documented.
