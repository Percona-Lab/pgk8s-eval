**Operator version:** 3.1.0, pgBouncer image percona-pgbouncer:1.25.2-6 (default cr.yaml, 3 replicas)
**Environment:** k3s v1.35.9+k3s1, 1 control-plane + 3 workers (Linode 2 vCPU / 4 GB, Ubuntu 24.04), local-path storage, S3-compatible object store with TLS.

## Summary
With the default pgBouncer setup, every failover or switchover costs **10–15 s more** through `cluster1-pgbouncer` than through `cluster1-primary`. During that window clients get a misleading `FATAL: SSL required` instead of an error that says the server is unavailable.

## Measurements (new connection + INSERT every ~200 ms)
| Scenario | Write outage, direct `cluster1-primary` | Write outage, via `cluster1-pgbouncer` |
|---|---|---|
| Primary pod deleted | 2.4 s | 13.1 s |
| Postmaster kill -9 | 10.8 s | 20.1 s |
| Planned switchover (documented procedure) | 2.4 s | 15.6 s |
| Primary deleted, operator scaled to 0 | 3.4 s | 17.6 s |
| Primary node power-off | 26.9 s | 47.2 s |

Client error during the gap (psql, default `sslmode=prefer`):
```
connection to server at "cluster1-pgbouncer.postgres-operator.svc" (10.43.43.233), port 5432 failed: FATAL:  SSL required
```
psql first tries TLS, fails because pgBouncer cannot reach a backend, then retries without TLS, which pgBouncer rejects (`client_tls_sslmode=require`). The real cause is hidden.

## Likely cause
pgBouncer's default `server_login_retry = 15` s: after one failed backend connect, pgBouncer waits up to 15 s before retrying the (already promoted) new primary.

## Suggestion
- Ship a lower default `server_login_retry` (e.g. 1–2 s) in the generated pgbouncer.ini, and document tuning via `spec.proxy.pgBouncer.config.global`.
- Document the misleading client error in troubleshooting.
