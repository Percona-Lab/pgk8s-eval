**Operator version:** 3.1.0
**Environment:** k3s v1.35.9+k3s1, 1 control-plane + 3 workers (Linode 2 vCPU / 4 GB, Ubuntu 24.04), local-path storage, S3-compatible object store with TLS.

## Summary
A cluster whose only backup repo is broken (S3 returns **403** because of a wrong secret key) reports **`ready`** in `kubectl get pg`. The real error is only visible as Warning events on the internal `postgrescluster` object, not on the `PerconaPGCluster` that users create.

## Steps
1. Create a PerconaPGCluster with a single S3 repo (repo1) and a `configuration` secret with a wrong `repo1-s3-key-secret`.
2. Wait 3 minutes.

## Observed
```
$ kubectl get pg ts-s3
NAME    ENDPOINT                                STATUS   POSTGRES   PGBOUNCER
ts-s3   ts-s3-pgbouncer.postgres-operator.svc   ready    1          1
```
Conditions: `ReadyForBackup=False PGBackRestReplicaCreate`, `PGBackRestReplicaRepoReady=False StanzaNotCreated: pgBackRest replica create repo is not ready for backups` (no mention of the 403).
Events (on `postgrescluster/ts-s3`):
```
Warning UnableToCreateStanzas ... ERROR: [039]: HTTP request failed with 403 (Forbidden):...
```

Similar for other faults: a bad image tag (pod `Init:ImagePullBackOff`) and a missing StorageClass (PVC `Pending`) both show only `initializing` with the same pgBackRest-related conditions; nothing names the real problem.

## Expected
- Top-level status should not be `ready` when no backup repo is usable (or there should be a clear `BackupsReady=False` with the message).
- Events and condition messages should be raised on the PerconaPGCluster object and carry the underlying error (403, ImagePullBackOff, PVC Pending).
