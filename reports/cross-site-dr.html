Percona Operator for PostgreSQL 3.1.0 vs CloudNativePG 1.30.1
Cross-site switchover and site-loss lab, 14 Oct 2026
Disaster recovery across sites

CloudNativePG's DR edge is a handshake, not a feature list

Both operators keep a replica cluster at a second site, and neither fails over across sites automatically. When a whole site died, both promoted the survivor in about 5 seconds and, with streaming, lost nothing. Neither stopped the dead site from coming back as a second primary, and neither could rejoin it without a rebuild. The difference showed up in planned site switches. CloudNativePG's demotion and promotion token made a switch over object storage alone lose nothing and rejoin cleanly. Percona has no such handshake, and over object storage the old primary was left unusable. With streaming between sites, Percona was faster and repaired itself. Both products can still be made to run two primaries.

A planned site switch, step by step

The sites share an S3 bucket. Each operator was driven the way its documentation, or for Percona the obvious procedure, implies.

CloudNativePG distributed topology

One field per cluster, plus a token

  1. Set replica.primary: dr-b on the site-A cluster. Writes stop.
  2. The operator archives the final WAL segment as .partial and publishes status.demotionToken (shutdown checkpoint LSN, timeline, system ID).
  3. Copy the token into site B as replica.promotionToken and set replica.primary: dr-b.
  4. Site B replays up to the token's LSN, then promotes.
  5. Site A follows site B from the archive: same pod, same volume.

Guarantee: no committed transaction is lost, and the old primary can follow, even with object storage as the only link.

Percona standby clusters

No procedure documented; two toggles

  1. Set standby.enabled: true (with repoName, plus host for streaming) on site A. Patroni demotes it.
  2. Wait until site B's replay position stops moving. This is a manual judgement call.
  3. Set standby.enabled: false on site B. Patroni promotes it.
  4. With streaming: site A follows site B, and Patroni runs pg_rewind if it diverged.
  5. Object storage only: site A's last WAL never reached the bucket, so it diverges and stays stuck.

Guarantee: none from the operator. Safety depends on the wait in step 2 and on having a streaming path.

Unplanned site loss

The most important DR case: site A disappears without warning. All four site-A VMs were powered off at once. After 60 seconds, the time someone takes to decide, site B was promoted. Five minutes later site A was powered back on and left alone, then told to follow site B.

Site A

k3s, 4 VMs in Atlanta. Primary cluster, 2 instances per operator.

Site B

Separate k3s, 3 VMs in Newark, 20 ms away. Replica or standby cluster, 2 instances.

Third site

Dallas: S3 object storage with TLS, plus clients writing about 16 commits per second and logging every acknowledgement.

What this means for Percona

  • Streaming DR works: zero loss and about 5 s to promote once someone decides.
  • Object storage alone: the 1-minute archive interval lost 50 s of writes; CloudNativePG's 5-minute default lost everything in the test window.
  • The shared repo is a hazard and an opportunity. A returning site wrote its own timeline into it and blocked new replicas at the surviving site. In the other run, site B's timeline in the same repo stopped the returning site from starting. The operator could use the same check deliberately to fence a returning site.

What this means for CloudNativePG

  • Promotion without a token is the only option after real site loss, so the token gives no protection here.
  • The returning site came back as a primary in both runs and reported "Cluster in healthy state" before and after the failed rejoin.
  • Separate archive paths per site kept the survivor clean. That is the one structural advantage seen in site loss.

One run per mode. Stale clients reconnected to the returning site when their dead TCP sessions were reset, after 1.5–3 min. The zombie-write counts depend on that client behaviour; any write accepted there is lost.

Issues found

Both products have DR hazards. CloudNativePG's are procedural; Percona's are structural.

Percona

  • No switch handshake. Over object storage, the demoted primary's last WAL never reaches the bucket. The new primary promotes without it, and the old primary can't follow. #1868
  • Stuck standby is invisible. The diverged old primary looped with no condition or Event. #1869
  • No dual-primary guard. Promotion is accepted while the source is still primary. #1869, #1862
  • Recreated cluster skips its first backup. A leftover PerconaPGBackup made status claim a backup existed; the DR site then could not bootstrap ("no backup set found"). #1867
  • A returning site can poison the shared repo. After site loss, the old primary came back, promoted to timeline 3 and archived it. New replicas at the surviving site then followed timeline 3 and could not start. The only fix was deleting files from S3 by hand. Not filed yet.
  • No fencing and no rejoin after site loss. In one run the returning site served writes for about 6 minutes, until it was told to follow site B. When told to follow site B, both members failed, patronictl reinit refused, and only wiping the volumes worked. #1869
  • No delayed standby. #1870
  • No role-swap documentation, no RPO guidance, and no explanation of repo-only vs streaming behaviour. docs #458

CloudNativePG

  • Leftover token trap. After a switch, the new primary keeps promotionToken in its spec. Demoting it later fails validation ("promotionToken is only allowed for primary clusters") unless the token is removed. A script that carries on promotes the other side anyway.
  • Promotion without a token is accepted even while the other cluster is still primary. The result was 170 s of two primaries and 5,604 lost writes.
  • Healthy status on a dead site. The diverged cluster reported "Cluster in healthy state" while PostgreSQL could not start.
  • 5-minute default archive interval. An object-storage-only DR site can be up to 5 minutes behind on a quiet primary.
  • Returning site is a second primary. In both site-loss runs the old site came back writable, still "healthy", and could not follow site B ("timeline 2 is not a child").
  • Rebuilding the old site needs undocumented steps. Recreating it failed with "Expected empty archive" until it got a new serverName; on an idle primary the rebuild then waited for the 5-minute archive interval.
  • Not filed with CNPG yet.

Opportunities for Percona

Percona already has the stronger engine for streaming DR. The gaps are the handshake, the guardrails and the documentation.

What to say in a deal

Claim you will hearResponse backed by this test
"CloudNativePG has better cross-cluster DR."Only for planned switches over object storage alone. With streaming between sites, Percona switched with zero loss in 1.9 s and repaired the old primary automatically. CloudNativePG's default archive interval is 5 minutes against Percona's 1.
"CloudNativePG's token makes switchover safe."When followed exactly. One leftover field made a demotion fail while the promotion went through: two primaries for 170 s, 5,604 writes lost, and a site reporting healthy while down.
"What happens if we lose a whole site?"Measured: with streaming, zero acknowledged writes lost on both operators, and writes resumed about 5 s after the promote command. Over object storage only, Percona lost 50 s against CloudNativePG's 64 s or more, set by the 1- vs 5-minute archive interval. Neither operator fences the dead site when it returns, so the runbook must keep it isolated until it is rebuilt.
"CloudNativePG keeps the surviving site safer."Partly true: its separate archive paths kept a returning site's WAL away from the survivor, while Percona's shared repo was polluted once. But CloudNativePG brought the dead site back as a primary in both runs and reported it healthy throughout.
"Percona can't swap sites without rebuilding."False with streaming: the old primary rejoined in every streaming run. True over object storage only, and fixing it is on the roadmap (#1868).

Method and limits

  • Planned switches: two namespaces simulated two sites in one k3s cluster on a LAN, with one PostgreSQL instance per site.
  • Unplanned site loss: two separate k3s clusters in different regions (Atlanta and Newark, 20 ms apart), with S3 and clients in Dallas. Two instances per site; cross-site streaming over NodePorts with copied replication certificates. Site A was lost by powering off all its VMs at once.
  • One run per scenario. Data volume was about 30 MB, so rebuild times are a lower bound.
  • CloudNativePG used object storage only (its documented distributed-topology example). Its streaming mode was not tested.
  • Scripts, manifests and raw logs: Percona-Lab/pgk8s-eval/dr, siteloss, results/dr_* and results/siteloss.
