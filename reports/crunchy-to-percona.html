Crunchy PGO v6.0.3 → Percona Operator for PostgreSQL 3.1.0
Hands-on lab, 14 Oct 2026
Crunchy Data replacement evaluation

Replace Crunchy. Keep the data, the passwords and the cron jobs.

Percona's operator is a fork of Crunchy PGO, and in the lab it behaved like it. Failover timings, split-brain safety, generated PostgreSQL and pgBouncer configuration, Secret format and pgBackRest layout were all the same. All three documented migration methods moved a Crunchy v6.0.3 cluster with zero data loss. Each one also hit a trap a customer would hit too: extensions dropped silently, passwords rotated, scheduled jobs left dormant, a rollback that isn't one, or a volume that never binds. Fix these and Percona is the natural landing place for Crunchy users before Crunchy's final planned releases.

Identical in both

  • =PostgreSQL parameters generated by default (wal_level, archive_timeout, pgaudit preload, scram, ssl)
  • =pgBouncer configuration, auth_query and _crunchypgbouncer/_crunchyrepl roles
  • =Service names (-primary, -ha, -replicas, -pgbouncer) and Secret keys (uri, pgbouncer-uri, jdbc-uri, verifier…)
  • =pgBackRest stanza db and repository layout; Percona restored Crunchy's S3 backup directly
  • =OS and libc in the images (RHEL 9.8, glibc 2.34), so no collation rebuild was needed
  • =Both operators ran side by side for 3 hours without interfering (Percona's 3.0 API group rename works)

Different, and it breaks things

  • ≠Primary pod label: Crunchy role=master, Percona role=primary. NetworkPolicies, alerts and scripts must change
  • ≠Image extensions: only Crunchy has pg_partman, pg_jobmon, timescaledb, orafce, plpython3u (+3 transforms), hypopg, passwordpolicy, pg_parquet, pgnodemx. Only Percona has pg_repack, pg_stat_monitor, pg_tde
  • ≠Extension management: Percona drops built-in extensions that are not enabled in its CR, in all databases
  • ≠pg_cron: Percona forces cron.database_name=postgres
  • ≠Per-user schema: Percona creates it by default; on Crunchy the same unqualified CREATE TABLE was refused in public
  • ≠Logs: Crunchy v6 writes to /pgdata/logs/postgres; Percona to log plus a Fluent Bit sidecar (6 containers vs 4)
  • ≠Install scope: Crunchy cluster-wide by default, Percona namespace-scoped

The traps, in detail

Each trap was reproduced in the lab. None is in Percona's migration guides today.

T1

Built-in extensions not enabled in the CR are dropped in every database

Silent data-feature loss

What happened

After a backup-and-restore migration with the documented cr.yaml, pg_stat_statements and set_user had been removed from the hippo database. The source code confirms the cause: when a built-in is disabled, the operator runs DROP EXTENSION IF EXISTS in all databases. Defaults disable pg_stat_statements, set_user, pg_repack and pg_cron.

Customer impact

Objects that depend on the extensions break; set_user privilege rules vanish; statistics history is lost. Nothing reports it.

T2

pg_cron jobs migrate but never run

Silent

What happened

Without pg_cron enabled, it is not preloaded. Enabling it forces cron.database_name=postgres, so both jobs scheduled in the application database (partman maintenance and a heartbeat) stayed in cron.job and never ran again.

Customer impact

Partition maintenance, purges and rollups stop. pg_partman tables eventually run out of partitions.

T3

Application passwords change at cutover

Outage

What happened

With users: [hippo] and no pre-created Secret, Percona generated a new password and applied it at promotion. The Crunchy password then failed with password authentication failed. Copying the Crunchy Secret (password + verifier) to <cluster>-pguser-hippo first kept it working.

Customer impact

Every application fails to log in right after cutover, unless someone knew to copy Secrets.

T4

Shared repo: rollback text is wrong, and nothing stops two writers

Data integrity

What happened

The standby method has both clusters use the same pgBackRest repo path. While Crunchy sat in standby after cutover, it replayed WAL that Percona had archived after promotion. When Crunchy was brought back, it already contained "first write on percona". The guide says the opposite: post-cutover writes "are not on Crunchy". Our test also skipped the guide's step that puts Percona back into standby. Both clusters then ran as primaries, on timelines 7 and 6, archiving into the same repo with no error.

Customer impact

Readers may copy post-cutover data back by hand and duplicate it. If the demotion step is missed or fails, the shared backup repository silently holds two diverging histories.

T5

Volume reuse hangs on topology-bound storage

Outage until fixed

What happened

The guide binds the migrated PV through a PVC selector. With a WaitForFirstConsumer StorageClass, the scheduler picked a node the PV could not attach to. The provisioner then rejected the selector ("claim.Spec.Selector is not supported") and the pod stayed Pending for 10 minutes. Pinning the instance to the PV's node fixed it in 26 s. Zonal cloud disks can hit the same issue.

Customer impact

Downtime grows without bound mid-migration, at the step that is hardest to roll back.

T6

Extensions that only Crunchy ships

Breaks code paths

What happened

The migrated plpython3u function failed with could not access file "plpython3". Physical migration copies catalog entries but not shared libraries. pg_partman worked (pure SQL), but its background worker and pg_jobmon are not available.

Customer impact

Failures appear only when the code path runs, which can be days after cutover.

T7

Smaller behaviour changes

Plan for them

What happened

  • Unqualified CREATE TABLE by the app user went to a new hippo schema (Percona autoCreateUserSchema defaults to true).
  • After standby promotion the cluster still serves Crunchy's certificate, issued by postgres-operator-ca for hippo-* names. verify-full clients fail on the new service names, and nothing renews it.
  • Pod label role=master becomes role=primary.
  • Service names change with the cluster name (hippo-primary → <cluster>-primary).

Customer impact

Application, monitoring and security-policy changes that must be in the runbook.

Product: make it seamless

The prize is a migration that needs no data copy and no application change. Percona is closer to that than any other operator, because the on-disk and in-cluster formats already match.

P1

Never drop extensions the operator did not create

Before 31 DecImpact highEffort low

Why

Fixes T1 and part of T2 for every migrated cluster, and for existing Percona users who create extensions by hand.

What to do

  • Make each built-in tri-state: enabled, disabled (drop), unmanaged (default: leave alone)
  • At minimum, skip drops on clusters bootstrapped from a dataSource or standby
P2

A Crunchy migration assistant

Before 31 DecImpact highEffort medium

Why

Every trap above came from a manual translation step.

What to do

  • kubectl pg migrate-from-crunchy (or a PerconaPGMigration CR) that reads a PostgresCluster (v1beta1 and v1) and writes a PerconaPGCluster
  • Preflight: PG major, arch, glibc/ICU, extensions in use vs the target image, shared_preload_libraries, cron.database_name, WAL/tablespace volumes
  • Copies user Secrets, maps repos (repo2→dataSource repo1), extensions, autoCreateUserSchema=false, labels to retarget
  • Generates the cutover and rollback runbook for the chosen method
P3

Respect cron.database_name

Before 31 DecImpact highEffort low

Why

Fixes T2. Crunchy users commonly run pg_cron in the application database.

What to do

Default to postgres but honour a value set in config.parameters or Patroni dynamic configuration, and create the extension in that database.

P4

Adopt a running Crunchy cluster in place

3.2Impact very highEffort high

Why

Labels, Services, Secrets, Patroni scope, pgBackRest stanza and data layout already match. Taking over the StatefulSets with a rolling image swap would turn migration into a rolling restart: no copy, no new endpoints, no password change. No other operator can offer this.

What to do

  • An adoption mode that takes ownership of existing PostgresCluster children after the Crunchy operator is scaled down
  • Keep names and Secrets; swap images one instance at a time with switchover
P5

Ship a Crunchy-compatible extension set and PostGIS 3.6

3.2Impact highEffort medium

Why

Fixes T6. pg_partman and plpython3u are common in Crunchy shops.

What to do

Add pg_partman (with its background worker), pg_jobmon, orafce, plpython3u, hypopg and TimescaleDB (Apache edition) to the image or as signed extension bundles; bump PostGIS to 3.6.

P6

pgMonitor-compatible metrics and OpenTelemetry

3.2Impact highEffort medium

Why

Crunchy users have Grafana dashboards and alerts built on ccp_* metrics. Losing them makes migration an observability project too.

What to do

An optional exporter sidecar with pgMonitor-compatible queries and metric names, plus an OTel output. Keep PMM as the upgrade path.

P7

Protect the backup repository on standby migrations

3.2Impact highEffort medium

Why

Fixes T4.

What to do

Read from the source repo while in standby, but write to a new repo path after promotion. Refuse to archive into a repo whose latest timeline belongs to another writer.

P8

Keep or replace certificates deliberately

3.2Impact mediumEffort low

Why

Fixes T7's certificate issue.

What to do

Support importing the Crunchy CA as customRootCATLSSecret so the operator issues new server certificates that clients already trust. Replace the borrowed certificate after promotion.

P9

Close the v6 feature gaps

3.2–3.3Impact mediumEffort medium

Why

v6 users compare feature for feature.

What to do

  • A controller for the already-installed PGAdmin CRD
  • Auto-grow on by default, with thresholds
  • Temp volumes and additional volumes on any container
  • Service traffic and IP family policies
  • Patroni logging settings
P10

Volume reuse that works on any storage

3.2Impact mediumEffort low

Why

Fixes T5.

What to do

Support volumeName in dataVolumeClaimSpec (static binding), or derive node affinity from the PV automatically. Accept WAL and tablespace PVs through dataSource.volumes.

P11

Compatibility switches

3.3Impact lowEffort low

Why

Lets customers defer app and policy changes.

What to do

Optionally also label the primary role=master; default autoCreateUserSchema=false on migrated clusters.

Documentation

The checklist page is good. The method pages need a "what is not migrated" list and fixes for each trap.

D1

"What is not migrated" on every method page

NowImpact high

Content

Passwords and Secrets, extensions and preload settings, pg_cron jobs, monitoring and dashboards, pgAdmin, certificates, Service names, labels, schedules.

Steps to add

  • Copy <cluster>-pguser-* Secrets before cutover
  • Map source pg_extension and shared_preload_libraries to spec.extensions; warn that disabled built-ins are dropped
  • Move pg_cron jobs to the postgres database (until P3)
D2

Cover PGO v6 and the v1 API

NowImpact high

Content

A tested-version matrix (5.6, 5.7, 5.8, 6.0) and v1 manifests. These tests show the guides work against 6.0.3 once the traps are handled.

Also

A field translation table: service→expose, shutdown→pause, paused→unmanaged, TLS fields under secrets, monitoring→PMM, autoGrow→gate.

D3

Fix the standby method's repo and rollback

NowImpact high

Content

Correct the rollback text: with the shared repo, post-cutover writes do come back to Crunchy. Require checking that Percona is in recovery before promoting Crunchy. Recommend a separate Percona repo path after the post-migration backup, and add certificate replacement after cutover.

Evidence

T4 and T7 above.

D4

Restore from Crunchy's real repo layouts

NowImpact medium

Content

Crunchy's default repo1 is a PVC, so S3 is often repo2. Show the dataSource mapping (repoN path → repo1 with repo1-* keys) and a path for PVC-only repos.

Related

k8spg-docs #451

D5

Make volume reuse safe

NowImpact medium

Content

Shut Crunchy down cleanly (spec.shutdown: true) before removing finalizers. For WaitForFirstConsumer or zonal storage, pin the instance to the PV's node or zone. Handle separate WAL and tablespace volumes.

Evidence

T5 above.

D6

Application cutover checklist

NextImpact medium

Content

Service names, the role label change, the per-user schema default, extension-dependent code paths (plpython, partman background worker), dashboards and alerts.

Why

Most post-migration incidents in these tests would surface in the application, not the database.

Method

  • Same lab as the CloudNativePG comparison: 4 × Linode 2 vCPU / 4 GB, k3s 1.35.9, local-path storage, S3-compatible store with TLS.
  • Crunchy PGO v6.0.3 installed cluster-wide from config/default at the v6.0.3 tag (namespace pgo), cluster hippo (3 × PG 18.6, pgBouncer, repo1 PVC + repo2 S3) in namespace crunchy. Images from the Crunchy Developer Portal, used for evaluation only.
  • Percona Operator 3.1.0 targets mig-restore, mig-standby, mig-volume with the rebuilt images (18.6.1-3, pgBouncer 1.25.2-8, pgBackRest 2.59.1-2).
  • Failover and split-brain used the same probe, writer ledger and pod-level partition as the CloudNativePG tests. One run per scenario.
  • Not tested: Crunchy 5.8 as a source (docs cover it), WAL and tablespace volumes, OTel, migrations across PG major versions.
  • Scripts, logs and the research notes are in Percona-Lab/pgk8s-eval.
