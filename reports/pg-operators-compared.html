PostgreSQL on Kubernetes

Percona Operator vs CloudNativePG

Percona Operator for PostgreSQL 3.1.0 is the stronger database-reliability product. CloudNativePG 1.30.1 is the stronger Kubernetes-operations product and has far more mindshare. Both were installed from their own docs on identical hardware, then failed, backed up, restored and broken on purpose. A follow-up on 14 Oct reproduced the publicly reported CloudNativePG split-brain on 1.30.1; Percona showed no dual-primary window under the same fault.

Shared weakness

Both operators let one backup pod become a hidden single point of failure. When the node holding the pgBackRest repo-host (Percona) or the Barman Cloud plugin (CloudNativePG) died along with the primary, failover took 4.5 to 6.5 minutes instead of 30 to 75 seconds. Neither project documents this or spreads these pods by default.

Biggest risks for Percona in deals

  • CloudNativePG's community momentum and CNCF branding
  • No kubectl plugin
  • Thin HA documentation, with a factual error on Patroni timings
  • pgBouncer in the default path adds 10–15 s to every failover
  • Percona now sells CloudNativePG support too, which blurs the message

Failure and recovery

A write probe opened a new connection and ran an INSERT every ~200 ms against each endpoint while we broke things. Outage = last successful write before the event to the first one after it.

Split-brain depends on the partition shape

When clients were cut off along with the node, neither operator split. When only the primary was cut off and clients kept their sessions, CloudNativePG ran two primaries for 129 s. See Split-brain.

pgBouncer costs Percona 10–15 s

pgBouncer's server_login_retry default of 15 s delays reconnection to the new primary. Clients meanwhile see FATAL: SSL required, because psql's sslmode=prefer fallback hides the real error.

Permanent node loss

Percona has no documented procedure; force-deleting the pod and its PVC recovered everything in 24 s. CloudNativePG's kubectl cnpg destroy left the pod Terminating until it was force-deleted, then healed in 32 s.

Split-brain

The publicly reported CloudNativePG split-brain still reproduces on 1.30.1 with default settings. Under the same fault Percona's Patroni demoted the isolated primary before a replacement existed, so it never ran two primaries.

The fault follows Coroot's method: the primary pod is cut off from its replicas, the operator and the API server, while three clients keep persistent connections and insert every ~100 ms. Every acknowledged write is checked against the final table. The issue is tracked as cloudnative-pg #11280, still open; the code fix (lease-based self-fencing) is planned for 1.31 and will not be backported.

Why CloudNativePG splits

Its isolation check only fails the liveness probe. The kubelet then triggers a smart shutdown, which refuses new sessions but lets open ones keep committing for up to smartShutdownTimeout (180 s). Meanwhile the operator promotes a replica. Setting smartShutdownTimeout: 0 or quorum sync closes the window today.

Why Percona doesn't

Patroni must renew its leader key in the Kubernetes API. When it can't, it demotes the primary itself, which ends open sessions, after 10–19 s. A replica can only take the key after the 30 s TTL, so demotion always comes first. Writes acknowledged before demotion are still lost with async replication.

Architecture

The core difference is where the failover decision lives. Percona runs Patroni in every PostgreSQL pod with the Kubernetes API as its lock store. CloudNativePG's operator detects failures and promotes replicas, so failover also needs the operator, and in 1.30 its backup plugin.

Installation & day one

Both quickstarts worked word for word. CloudNativePG reached a running cluster twice as fast. Percona's cluster arrived more complete: pooler, backups and a first full backup already running.

  • Percona's v3.1.0 cr.yaml installs older image builds than its release notes recommend (18.6.1-1 vs -3, pgBouncer 1.25.2-6 vs -8, pgBackRest 2.59.0-1 vs 2.59.1-2). The rolling update to the right tags took 112 s with a 3.4 s write gap.
  • Percona switches to cert-manager automatically when it finds one (certManagementPolicy: auto). That helps on clusters that standardize on cert-manager and surprises everyone else.
  • Crunchy heritage still shows: postgres-operator.crunchydata.com/* labels and a Crunchy-named switchover annotation.
  • pgBackRest only speaks HTTPS to S3; a plain-HTTP lab endpoint won't work. MinIO no longer publishes container images, although both doc sets still use it in examples.

Backup, restore & PITR

Both recovered a dropped 2,000,000-row table to the exact point in time, as documented. Percona's restore model is more flexible and was faster.

  • The ~5-minute default backup affects both. They wait for a spread checkpoint. Neither quickstart mentions it.
  • Percona clone trap: the dataSource repo must be repo1, so its secret needs repo1-* keys even when the source wrote to repo2.
  • Percona repo-host loss stops all WAL archiving, even to the healthy S3 repo, so WAL piles up on the primary.
  • CloudNativePG backs up from a standby by default; Percona reads from the primary.
  • CloudNativePG's in-tree Barman is removed in 1.31. Existing users face a forced migration to a v0.x plugin.

CloudNativePG

  • kubectl cnpg: status, report, promote, destroy, backup, psql, fencing, hibernate
  • Events on the Cluster resource
  • Prometheus exporter on every pod: 482 cnpg_* metric lines with no setup
  • Logs as JSON to stdout; shipping is up to you

Percona

  • No CLI: kubectl exec into patronictl and pgbackrest
  • Warnings land on the internal postgrescluster, not the user's CR
  • PostgreSQL metrics need a PMM server; in return you get query analytics and dashboards
  • Fluent Bit + logrotate sidecars keep logs across restarts

Documentation

Tied at 7.4 out of 10, with mirror-image strengths. Percona's docs say how to do each task. CloudNativePG's explain what happens when things fail.

Percona docs vs reality

  • Reference says leaderLeaseDurationSeconds is a probe delay; it is the Patroni TTL that set our ~30 s outage
  • No page on pod or node failure, and no node-loss runbook
  • Live errors: PXC hostname in debug-shell, Running instead of ready, HH:MM:DD, PG 13 in compare

CloudNativePG docs vs reality

  • Node-failure timing matched the docs
  • cnpg destroy on a dead node needs an undocumented force-delete
  • No warning that a plugin outage blocks failover
  • Leftover chatbot line on the 1.30 supported-releases page; old links redirect to devel

Objections and responses

ObjectionResponse backed by this test
"CloudNativePG is the CNCF standard"OpenEverest, built on Percona's operator, is also CNCF Sandbox. CloudNativePG's maintainers all work at EDB.
"Patroni in a pod is legacy"Patroni failed over in 3.4 s with the operator down; CloudNativePG could not. It was also fastest on node loss (27–31 s vs 74–98 s).
"CloudNativePG has no split-brain"On 1.30.1 with defaults it ran two primaries for 129 s and lost 3,680 acknowledged writes during the overlap. The fix ships in 1.31; until then users must set smartShutdownTimeout: 0 or quorum sync.
"CloudNativePG backups are fine"They need cert-manager, a v0.x plugin and an object store first. In-tree removal in 1.31 forces a migration, and there is no in-place restore.
"CloudNativePG is easier to operate"True for tooling: plugin, Events, native metrics. Percona should close this gap.

Recommendations for Percona

Fix the two failover problems the tests exposed, ship a kubectl plugin, and market the measured HA advantage.

Product

  1. Stop the repo-host from blocking promotion: fail archive-get fast during promotion and add anti-affinity
  2. Default pgBouncer server_login_retry to 1–2 s and surface a meaningful client error
  3. Ship a kubectl plugin: status, switchover, backup, restore, report, psql
  4. Put real errors in PerconaPGCluster status and Events; never ready with no working repo
  5. Make switchover a single action
  6. Offer native Prometheus metrics next to PMM
  7. Default --start-fast; keep cr.yaml image tags current

Docs

  1. Add a failure-scenarios page with these timings
  2. Fix the Patroni timing reference and explain the Kubernetes DCS
  3. Add a node-loss runbook and a clone example from repo2
  4. Fix the live-site errors

Go to market

  1. Lead with resilience: "fails over even when the operator is down" and "no split-brain under partition"; publish the harness
  2. Target CloudNativePG's backup transition with a migration guide
  3. Frame Percona's CloudNativePG support as a path to OpenEverest, PMM and pg_tde

Method & limits

Lab

  • 4 × Linode g6-standard-2 (2 vCPU, 4 GB), Ubuntu 24.04, us-southeast
  • k3s v1.35.9: 1 tainted control-plane node, 3 workers, local-path storage
  • S3-compatible store with TLS on the control-plane node
  • pgbench scale 20 (337 MB) in both clusters
  • Write probes on the control-plane node against Percona cluster1-primary, Percona cluster1-pgbouncer and CNPG cluster-example-rw
  • Split-brain runs: 3 persistent-connection writers with a per-commit ledger; partitions applied with iptables inside the primary pod's network namespace; VM pause approximated by freezing the pod cgroup and stopping the kubelet

Limits

  • One run per scenario on small VMs
  • Network-attached volumes would change node-loss recovery
  • pgBouncer tuning not re-tested
  • PMM, major upgrades, cross-cluster DR and pg_tde assessed from docs only
